Protocol Auto-Detection

The ESP DRONE REMOTEID identifies the UART protocol by looking for specific headers. In auto mode (the default, protocol = 255) detection runs continuously and is re-evaluated on every loop iteration, reading up to 50 ms of UART data per pass. The headers are checked in this order:

flowchart TD
  Start["Boot / Reset"]
  Listen["Read UART up to 50 ms"]

  MSP{"$M< ?
MSP v1 header"}
  NMEA{"$G or $N prefix?
NMEA 0183"}
  MAVLink{"0xFE or 0xFD?
MAVLink v1/v2"}
  Fallback["Fallback: NMEA"]

  MSP_OK["✅ MSP"]
  NMEA_OK["✅ NMEA"]
  MAV_OK["✅ MAVLink"]

  Main["Run main loop"]

  Start --> Listen
  Listen -->|no data| Main
  Listen --> MSP
  MSP -->|Yes| MSP_OK
  MSP -->|No| NMEA
  NMEA -->|Yes| NMEA_OK
  NMEA -->|No| MAVLink
  MAVLink -->|Yes| MAV_OK
  MAVLink -->|No| Fallback
  Fallback --> Main
  MAV_OK --> Main
  MSP_OK --> Main
  NMEA_OK --> Main
Protocol auto-detection priority order in auto mode: MSP, then NMEA, then MAVLink. NMEA is the fallback when a frame is present but no header matches. When no data arrives, the protocol shows as unknown until the next cycle.

In auto mode the detection result is applied immediately and re-evaluated every loop, so it is not stored between cycles. When a fixed protocol is configured (protocol = 1, 2 or 3), the matching parser is used directly without detection.

MAVLink (ArduPilot)

The firmware parses the following MAVLink v1/v2 messages (dialect: ardupilotmega):

MessageIDData UsedFrequency
GLOBAL_POSITION_INT33Latitude, longitude, altitude (MSL + relative), heading, relative alt~5 Hz
GPS_RAW_INT24Latitude, longitude, altitude (MSL), ground speed, satellites, fix type~5 Hz
VFR_HUD74Ground speed, heading, altitude (baro), climb rate~5 Hz
ATTITUDE30Roll, pitch, yaw (heading)~10 Hz
AHRS2178Secondary heading (ArduPilot), used as fallback~5 Hz
HEARTBEAT0System ID, vehicle type (for auto-detection)1 Hz
OPEN_DRONE_ID_LOCATION12915Pre-encoded ODID location (lat/lon/alt/alt_baro/vel/heading)~1 Hz
OPEN_DRONE_ID_BASIC_ID12900UAS ID, ID type, UA type (overrides config identity)~1 Hz
OPEN_DRONE_ID_OPERATOR_ID12905Operator ID from ground station~1 Hz
OPEN_DRONE_ID_SELF_ID12902Self-ID text description from ground station~1 Hz
OPEN_DRONE_ID_AUTHENTICATION12903Authentication pages from ground station~1 Hz
OPEN_DRONE_ID_SYSTEM12904Operator location (GPS fallback when FC has no fix)~1 Hz
OPEN_DRONE_ID_MESSAGE_PACK12919Packed ODID messages (multiple ODID messages in one MAVLink packet)~1 Hz

The MAVLink parser handles both v1 (0xFE start byte) and v2 (0xFD start byte) protocols. The system ID from the first HEARTBEAT message is used if mavlink_sysid = 0 (auto-detect). ODID messages override the config identity for compatibility with ArduPilot's native Remote ID support.

By default the firmware only listens on the UART. If the MAVLink arm status or MAVLink operator location loopback option (or MAVLink over USB) is enabled, a bidirectional link is started that sends a MAVLink HEARTBEAT (MAV_TYPE_ODID) every 1 s and republishes the ODID SYSTEM message every 6 s.

MAVLink Configuration Tips
  • Set the baud rate to match your ArduPilot serial port (57600 is common).
  • If using MAVLink v2, ensure the port is configured for MAVLink1 or MAVLink2.
  • The firmware only listens — it does not send any MAVLink messages, so it will not interfere with your existing telemetry link.

MSP (Betaflight / INAV)

The firmware parses the following MSP v1 messages:

MessageIDData UsedNotes
MSP_RAW_GPS106Latitude, longitude, altitude, speed, ground course, satellites, fix typePrimary GPS data source
MSP_ATTITUDE108Roll, pitch, yaw (heading in degrees)Heading for ODID message
MSP_STATUS101Armed state (bit 0 of flags)Used by the "force arm" option

The MSP parser expects the standard MSP v1 framing: $M< header, size byte, command byte, data payload, checksum. It does not require sending any request to the FC — it passively listens to the FC's MSP response stream (typically from the FC's telemetry output).

MSP Configuration Tips
  • Enable MSP on the desired UART in the Betaflight Configurator Ports tab.
  • Set baud rate to match (57600 is common for MSP).
  • INAV sends MSP_RAW_GPS automatically at ~5 Hz when armed.
  • Betaflight may require setting serialrx_provider = MSP for continuous GPS output.

NMEA 0183

The firmware parses the following NMEA 0183 sentences:

SentenceTypeData Used
$GPGGAGlobal Positioning System Fix DataLatitude, longitude, altitude (MSL), fix quality (0/1/2), satellites, HDOP
$GPRMCRecommended Minimum Specific GNSS DataSpeed over ground (knots → m/s), ground course, date, status (A=valid)
$GPVTGCourse Over Ground and Ground SpeedGround speed (km/h → m/s), course over ground (true)

The NMEA parser handles both $GP (GPS) and $GN (GNSS) prefixes. It does not validate the checksum field (the part after the *): sentences are parsed line by line and malformed or unrecognized sentences are silently discarded.

NMEA Configuration Tips
  • GPS modules typically output NMEA at 9600 or 115200 baud. Set the baud rate accordingly.
  • The NMEA mode requires the 1 kΩ series resistor on the TX tap line (see Hardware section).
  • NMEA mode works with any GPS module: BN-880, BN-220, M8N, M10, NEO-6M, NEO-8M, and many others.
  • The ESP32 can share the GPS TX line with the FC — the resistor prevents the ESP32's input capacitance from degrading the signal to the FC.

Method 1: WebSerial (Browser) — Recommended

The easiest method. Requires Chrome or Edge on Windows, macOS, or Linux. No Python or toolchain needed.

  1. Connect the ESP32 to your computer via USB.
  2. Install the CP2102 or CH340 driver if prompted (Windows usually auto-installs).
  3. Click the install button on the Quick Start page (index.html) — use the "Go to Quick Start" button in the left column of this page.
  4. A browser dialog will appear showing available serial ports. Select your ESP32 (usually labeled CP2102 USB to UART Bridge or CH340).
  5. Click Connect. The firmware will download and flash automatically.
  6. Wait for the progress bar to complete and the "Done" message.
  7. Disconnect USB and power the ESP32 from your flight controller's BEC or a USB power bank.
⚠ Note: WebSerial requires HTTPS (this page is served via GitHub Pages which is HTTPS). If running locally, use localhost or enable HTTPS.

First Boot & Verification

After flashing successfully, the firmware boots in one of two modes:

  • FC mode (default): Connect to a flight controller via UART for real GPS data.
  • Demo mode (optional): Enabled via the Options bit 3 (or the demo CLI command). Simulates a drone flying a circular patrol over Rome (Colosseum, ~300 m radius) at ~6 m/s, altitude 50±20 m. No flight controller needed. You can configure, view live telemetry, and test OTA immediately.

To toggle demo mode, use the config UI, the demo CLI command, or set options bit 3 (RID_OPT_DEMO_MODE).

  1. Power the ESP32 via USB or connect to your flight controller's BEC.
  2. Wait 10-15 seconds for the ESP32 to boot. The RGB LED (if configured) shows status: amber = no fix, green = fix OK, white flash on each transmission.
  3. Scan for WiFi on your phone or laptop. You should see a network named ESP-RID (or your custom SSID).
  4. Connect to ESP-RID (no password by default).
  5. Open a browser and navigate to http://192.168.4.1. The configuration page should load.
  6. Check the Status section — in demo mode, you'll see simulated GPS patrol data. With an FC connected, it shows the detected protocol and live GPS data.
  7. Verify Remote ID broadcast — use a smartphone app like Drone Scanner (iOS/Android) or OpenDroneID Viewer (Android) to confirm that Remote ID messages are being received.
LED Behavior

The status LED is an RGB LED driven via PWM on up to three configurable GPIOs (default: not configured / off). It shows one of 7 states plus a white flash on every transmission:

StateColor / PatternMeaning
BOOTBlue pulseESP32 initializing
NO_GPSAmber blink ~1 HzNo GPS fix, waiting for data
GPS_OKGreen solidGPS fix acquired, broadcasting Remote ID
DEMOPurple pulseDemo mode active
LOCKEDRed double-blinkLock level ≥ 1 active
OTARainbow cycleOTA update in progress
ERRORRed blink ~4 HzFirmware/configuration error
TX flashWhite ~80 msTransmission in progress (overrides all states)
First-Time Configuration Checklist
  1. Set your UAS ID (serial number or CAA registration) in the Identity section.
  2. Set your Operator ID if required by your local regulations.
  3. Verify the baud rate matches your flight controller's serial port speed.
  4. Enable the transmission modes you need (WiFi Beacon, BLE 4.0, BLE 5.0).
  5. Click Save All to persist settings.
  6. Reboot the ESP32 to ensure settings are applied correctly.

NVS Persistence

A subset of configuration parameters is stored in the ESP32's Non-Volatile Storage (NVS) flash memory under the namespace esp_rid and persists across power cycles, reboots, and OTA updates. The full key layout is in Technical Reference → NVS Key Layout. Parameters that are not persisted (protocol, UART port and TX/RX pins, WS2812, GPIO lighting, DroneCAN, MAVLink USB, OTA trigger GPIO, auth private key, startup delay) are runtime-only and reset to defaults on reboot. A factory reset erases the esp_rid namespace and restores defaults.

Step-by-Step Setup Walkthrough

Follow this sequence to configure your ESP DRONE REMOTEID for the first time. You can start in demo mode (no hardware needed) and switch to FC mode later:

StepActionDetails
1Set UAS IDNavigate to Identity tab. Enter your drone's serial number or CAA registration in the UAS ID field (max 20 characters). Example: RID-A1B2C3D4.
2Set ID TypeChoose Serial Number (1) for ANSI/CTA-2063 serial numbers, or CAA Registration (2) for national authority IDs.
3Set UA TypeSelect your aircraft type. Multirotor (2) is correct for most quadcopters and hexacopters.
4Set Operator IDEnter your operator registration number if required. Format varies by country (e.g., OP-MARIO-12345).
5Enable TransmittersIn the Transmission section, check at least WiFi Beacon and BLE 4.0. These are the most compatible modes. BLE 5.0 LR requires ESP32-S3 or ESP32-C6.
6Set Baud RateIn WiFi AP & Serial, set the baud rate to match your flight controller's serial port. Common: 57600 or 115200.

Interface Sections

Identity

Configure your drone's UAS ID, operator information, and aircraft type. The Basic ID is mandatory for ASTM compliance. The second Basic ID is optional and can be used for dual-purpose aircraft or additional identifiers.

  • UAS ID: Your drone's serial number (ANSI/CTA-2063 format) or CAA registration number. Max 20 characters.
  • ID Type: Select the type of identifier. Serial Number (1) is recommended for most users.
  • UA Type: Match your aircraft type. Multirotor (2) is the default for most drones.
  • Operator ID: Your national aviation authority registration number.
Transmission

Control which radio technologies are used for broadcasting and their parameters.

  • WiFi Beacon: IEEE 802.11 beacon frames containing ODID packets. Most compatible with receivers.
  • WiFi NAN: Neighborhood Area Networking. Less common, but supported by some Android devices.
  • BLE 4.0: Legacy Bluetooth Low Energy advertising. Compatible with most phones and ODID receivers.
  • BLE 5.0 LR: BLE 5.0 Coded PHY long range mode. Requires ESP32-S3 or ESP32-C6. Increased range at lower data rate.

Rates are in Hz (packets per second). The ASTM standard recommends at least 1 Hz. Higher rates increase compatibility but consume more power.

WiFi AP & Serial

Configure the management WiFi network and UART connection to your flight controller.

  • SSID: The name of the ESP32's WiFi network. Default: ESP-RID.
  • Password: Optional password (max 20 chars). Empty = open network.
  • Baud Rate: Must match your flight controller's serial port speed. Common: 57600, 115200.
  • MAVLink SysID: Set to 0 for auto-detect, or enter a specific system ID to filter messages.
System

Security settings, authentication, and advanced options.

  • Lock Level: 0 = normal operation. 1 = signed commands only. 2 = permanent eFuse (irreversible!).
  • Public Keys: Up to 5 public keys (PEM or base64) for authenticating signed configuration commands.
  • Auth Private Key: Ed25519 private key for authentication page signing (ASTM F3411-22a).
  • Options: Force ARM status, disable NVS saving of BasicID, enable MAVLink RID printing, demo mode, Kalman filter, Ed25519 auth, MAVLink arm status, MAVLink operator location loopback, identity ready gate.
Hardware

GPIO pin assignments and peripheral configuration.

  • Status LED (R/G/B): Three independent GPIO pins for RGB status LED. 7 states via PWM: BOOT, NO_GPS, GPS_OK, DEMO, LOCKED, OTA, ERROR.
  • WS2812 LED: Addressable RGB LED driven via RMT. Configurable GPIO and brightness (0-100%).
  • GPIO Lighting: 5 independent lighting outputs. Each channel configurable with GPIO pin, pattern (OFF/SOLID/BLINK_SLOW/BLINK_FAST/ARMED/GPS_FLASH), and phase offset in milliseconds.
  • DroneCAN: CAN bus receiver. Configurable RX/TX GPIO pins and bitrate (default 1 Mbps). Decodes uavcan.equipment.gnss.Fix2.
  • UART Pins: Select UART peripheral port (UART0/1/2) and assign any GPIO for TX and RX.
  • MAVLink USB: Enable MAVLink over USB CDC serial transport (ESP32-S3/C6 only).
  • OTA Trigger GPIO: GPIO that triggers OTA update mode at boot (firmware upload on next restart).
  • Startup Delay: Delay in milliseconds before transmission begins after boot (default 10 000 ms).
Operator Position

Fallback operator latitude, longitude, and altitude used for the ODID System message when no operator location is available (e.g., no MAVLink operator-location loopback).

Status

Real-time telemetry dashboard showing:

  • Detected protocol (MAVLink, MSP, NMEA, or None)
  • GPS fix status (valid/invalid)
  • Latitude, longitude, altitude, speed, heading
  • Satellite count and fix type
  • Transmission counters (total, WiFi, BLE)

The status page refreshes automatically every 2 seconds.

Click the "Factory Reset" button in the System section to restore all settings to defaults. The device will reboot immediately.

Over-the-Air Firmware Update

The ESP DRONE REMOTEID supports updating firmware wirelessly through the web interface. No USB cable is needed once the initial firmware is flashed. The upload process includes cryptographic verification to prevent corrupt or malicious firmware.

Prerequisites

  • A .bin firmware file built for your ESP32 target (ESP32, ESP32-S3, or ESP32-C6).
  • The ESP32 must be powered and connected to its WiFi network (you connected to ESP-RID).
  • Your phone/PC must be connected to the ESP32's WiFi network.

Step-by-Step

  1. Build the firmware (see section 4 → Building from Source) or download a pre-built .bin from the project's releases.
  2. Open the Web UI at http://192.168.4.1.
  3. Scroll to the Firmware Update section.
  4. Click Select .bin file and choose your firmware binary.
  5. The browser computes a SHA-256 hash of the file (via Web Crypto API) and sends it as the X-Expected-SHA256 header.
  6. Click Upload Firmware.
  7. Wait for the upload to complete (~30 seconds for a 1 MB firmware). The progress text will update.
  8. The server verifies the SHA-256 hash matches the received binary. If lock level ≥ 1, an Ed25519 signature (X-Signature header) is also required.
  9. On success, the device reboots automatically into the new firmware.

Verification Flow

The OTA update uses a two-layer verification process implemented in rid_security.c:

  1. SHA-256 integrity check: The browser computes SHA-256 of the firmware binary before upload. The server independently computes SHA-256 of the received data and compares it to the X-Expected-SHA256 header. Mismatches are rejected immediately.
  2. Ed25519 signature (lock level ≥ 1): When lock level is 1 or 2, an X-Signature header containing an Ed25519 signature over the SHA-256 hash must be provided. The signature is verified against the configured public keys.

OTA update flow: browser computes SHA-256 → sent as X-Expected-SHA256 header → server verifies hash + optional Ed25519 signature → writes to the ota_0 partition → reboots. Failed updates roll back to the factory image.
  1. The web server receives the firmware binary in an HTTP POST to /ota.
  2. It verifies the SHA-256 hash of the received data against the X-Expected-SHA256 header using the rid_security.c module.
  3. If lock level ≥ 1, it also verifies the Ed25519 signature against configured public keys.
  4. On success, it writes the binary to the ota_0 OTA partition.
  5. It sets the OTA partition as the boot partition and calls esp_restart().
  6. The ESP32 boots from the new firmware. If the update fails, the bootloader falls back to the factory image.

Safety

  • The default partition table has one factory partition and one OTA partition (ota_0). If an OTA update fails, the device falls back to the factory firmware.
  • SHA-256 verification prevents corrupt or incomplete firmware from being applied.
  • Ed25519 signature verification (lock level ≥ 1) prevents unauthorized firmware changes.
  • Always use a firmware built for your specific ESP32 target. Flashing an ESP32-S3 binary to an ESP32 will fail.
  • Keep the device powered during the update. Do not disconnect or reset.
  • If the update fails, you can always recover via USB serial flashing.

Up to 5 public keys can be configured (in PEM or raw base64 format). These keys are used to verify Ed25519-signed configuration commands when lock level 1 or 2 is active.

To generate a key pair:

# Generate Ed25519 private key

# Extract public key
openssl pkey -in private.pem -pubout -out public.pem

# The public key content (base64) goes into the public_key fields
cat public.pem

Signed Commands

When lock level ≥ 1, any POST to /api/config must include a signature header:

curl -X POST http://192.168.4.1/api/config \
  -H "Content-Type: application/json" \
  -H "X-Signature: <base64-ed25519-signature>" \
  -d '{"uas_id":"RID-12345678"}'

The signature is an Ed25519 signature over the SHA-256 hash of the JSON body. Failed signature attempts are rate-limited (10 per 60s sliding window).

WiFi Security

The configuration access point can be password-protected. Set a WiFi password in the Web UI to prevent unauthorized access to the configuration interface. The password is stored in NVS and can be up to 20 characters.

⚠ Note: The AP uses WPA2-PSK encryption when a password is set. Without a password, the network is open and anyone within range can access the configuration page.

Choosing the Right Antenna

Antenna selection is critical for Remote ID performance. The ESP32 operates in the 2.4 GHz ISM band and the antenna must be well-matched to achieve reliable broadcast range.

PCB Antenna (On-Board)
  • Pros: Low cost, no additional hardware, compact.
  • Cons: Vulnerable to shielding by carbon fiber frames, sensitive to placement within the drone.
  • Range: ~50-100 m in open air with clear line of sight.
  • Best for: Glass fiber, plastic, or 3D-printed frames. Open-frame builds.
External Antenna (U.FL / IPEX)
  • Pros: Can be placed away from shielding frame, better range, replaceable.
  • Cons: Requires board with U.FL connector, additional cost, mounting required.
  • Range: ~200-500 m with a 2 dBi dipole antenna.
  • Best for: Carbon fiber frames, long-range applications, professional use.

Carbon Fiber Frames

⚠ Critical: Carbon fiber is conductive and acts as a Faraday cage for 2.4 GHz signals. An internal PCB antenna placed inside a carbon fiber frame will have severely degraded range (<10 m). An external antenna is mandatory for carbon fiber frames.

Mount the external antenna so that it protrudes from the frame, ideally on a landing skid or a dedicated 3D-printed mount. Keep the antenna away from carbon fiber plates by at least 10 mm.

Antenna Placement Tips

  • Keep the antenna away from metal objects, batteries, and power cables.
  • Orient the antenna vertically for omnidirectional coverage (most drone receivers are also vertical).
  • Do not route the antenna coax cable parallel to power wires — cross them at 90° if necessary.
  • Do not coil or bundle excess antenna cable — it acts as a counterpoise and affects tuning.
  • Use a cable with a U.FL to SMA pigtail if your antenna uses SMA connectors.

Cannot Find ESP-RID WiFi

  • Wait 10-15 seconds after powering the ESP32 for it to boot and start the AP.
  • Check that the ESP32 is powered correctly (LED should be on if connected via status LED).
  • If you changed the SSID previously, scan all nearby networks.
  • Factory reset: connect via serial and erase NVS, or re-flash the firmware.
  • If the AP starts but you can't connect, try forgetting the network and reconnecting.

No Remote ID Signal Detected

  • GPS fix is required for transmissions in the current build — the "Broadcast without GPS" option currently has no practical effect. Check the Status page.
  • Verify that transmission modes are enabled in the Web UI (WiFi Beacon, BLE).
  • If using a phone as a receiver, use a dedicated ODID app (e.g., Drone Scanner, OpenDroneID Viewer).
  • WiFi Beacon requires the phone to be in range and scanning. Some phones do not passively scan WiFi beacons.
  • BLE 4.0 is more universally detectable than BLE 5.0 LR. Enable BLE 4.0 if BLE 5.0 is not detected.
  • Carbon fiber frame with internal antenna will have very short range. Use an external antenna.

WiFi AP Disconnects

  • The ESP32 can handle ~4-5 simultaneous WiFi clients. Too many clients may cause disconnections.
  • Move closer to the ESP32 (within 5 m for reliable connection).
  • Avoid interference from other 2.4 GHz devices (WiFi routers, Bluetooth, microwaves).
  • Try a different WiFi channel (1 or 11 are usually less congested).

Standards Compliance (targeted)

ESP DRONE REMOTEID targets the following standards (message encoding complete, compliance testing with certified receivers pending):

  • ASTM F3411-22a — Standard Specification for Remote ID and Tracking. This is the US FAA-accepted standard that also forms the basis for many international regulations.
  • ASD-STAN prEN 4709-002 — European standard for direct Remote ID, adopted by EASA and EU member states.

FAA (United States)

FAA Part 89 requires all drones weighing more than 0.55 lb (250 g) and flown outdoors to broadcast Remote ID. The regulation came into effect on September 16, 2023. ESP DRONE REMOTEID helps drone operators comply with this requirement by:

  • Broadcasting ASTM F3411-22a Standard Remote ID messages via WiFi Beacon and BLE
  • Transmitting at 1 Hz (meeting the minimum requirement)
  • Including all required data: drone ID, location, altitude, speed, operator ID

Note: Regulatory compliance with certified receivers has not been verified. Do not use in actual flight operations until testing confirms compliance.

EASA (European Union)

EU Implementing Regulation 2021/664 (U-Space) and 2019/947 require Remote ID for most drone operations in the Open and Specific categories. Direct Remote ID (prEN 4709-002) has been mandatory since January 1, 2024. The same framework applies in the EEA states (Norway, Iceland, Liechtenstein) and non-EU EASA states (Switzerland). ESP DRONE REMOTEID supports compliance by broadcasting Direct Remote ID (prEN 4709-002) over WiFi and BLE.

FCC / CE Compliance

ESP DRONE REMOTEID operates in the 2.4 GHz ISM band. The ESP32's WiFi and BLE transmitters are certified under FCC Part 15 and CE RED when used with Espressif's reference modules. Using external antennas may affect compliance. Ensure your antenna setup complies with local radio regulations.

Operator Registration

Most countries require drone operators to register with the national aviation authority and display their operator ID on the drone. ESP DRONE REMOTEID allows you to set your operator ID in the configuration, which is included in the System Message (Type 2) of the ODID transmission. Check your local authority's requirements:

  • USA: FAA DroneZone
  • EU: Register in your country's UAS system
  • UK: CAA Drone Registration
  • Japan: MLIT Drone Registration
  • Canada: Transport Canada Drone Portal
  • Australia: CASA Drone Registration
⚠ Disclaimer: This firmware is a tool to assist with Remote ID compliance. It is your responsibility to verify that your specific configuration meets local regulations. The authors are not liable for any regulatory violations or penalties.

Recommended Practices

  • Set your correct UAS ID (serial number or CAA registration).
  • Set your correct Operator ID.
  • Keep the firmware updated for regulatory changes.
  • Test that your Remote ID signal is receivable by standard ODID receiver apps before operational use.
  • Register your drone with your national aviation authority if required.
  • Use a dedicated Remote ID receiver app to verify your broadcast before each flight session.
  • Keep records of your UAS ID and operator registration for inspection if requested.

Adding a New Protocol

To add support for a new protocol:

  1. Create a new parser file in components/esp_remote_id/src/ and its header in include/
  2. Implement the standard parser interface: void xxx_parser_init(uint8_t uart_port) + bool xxx_parser_get(rid_gps_data_t *gps) (see nmea_parser.c, msp_parser.c, mavlink_parser.c)
  3. Add the protocol to rid_protocol_t in esp_remote_id.h and to the proto_name array in esp_remote_id.c
  4. Register the new protocol in the auto-detection sequence in protocol_detect.c
  5. Test with your hardware and submit a PR
